# 🎤 URL Shortener: Technical Interview Q&A

This document contains a comprehensive progression of technical questions and detailed answers regarding the architecture, implementation, and scaling of the URL Shortener project.

---

### Phase 1: High-Level Overview & Tech Stack

**1. Can you give a quick elevator pitch for this project? What problem does it solve?**
This project is a high-throughput URL shortening service designed to provide low-latency redirection for users. It solves the problem of sharing long, unwieldy URLs by converting them into short, manageable links. Additionally, it features multi-layer caching for extreme performance, non-blocking click-stream analytics, and real-time telemetry tracking to monitor link engagement.

**2. What technologies, frameworks, and tools did you choose, and why?**
- **Java 21 & Spring Boot 3**: Chosen for their robust enterprise capabilities and mature ecosystem. Spring Web is used for REST APIs, and Spring Data JPA handles database interactions.
- **PostgreSQL**: Selected for strict relational integrity and reliability when storing URL mappings and click telemetry.
- **Redis**: An in-memory data store used for sub-2ms cache lookups, ensuring redirects happen instantly without hitting the primary database.
- **Docker**: Used to containerize the database and cache for easy, reproducible local environments.
- **Vanilla HTML/CSS/JS**: Chosen for the frontend to create a lightweight, zero-overhead client without the complexity of a heavy framework like React.

**3. Walk me through the end-to-end lifecycle of shortening a URL.**
When a client sends a `POST /api/v1/urls` request, the payload is first validated by the Controller using `@Valid` to ensure it's a properly formatted URL. The Service layer then saves the original URL to PostgreSQL. Upon saving, PostgreSQL generates a unique numeric ID. We take this unique ID and encode it using a Base62 algorithm to generate a short, alphanumeric string. The entity is updated with this short code, the mapping is stored in the Redis cache for immediate availability, and a DTO containing the short URL is returned to the client.

**4. Walk me through what happens when a user clicks a shortened link.**
When a user navigates to `/{shortCode}`, the Controller intercepts the request. The application first checks the Redis cache (Cache-Aside pattern). If there is a cache hit, it immediately retrieves the original URL. If there is a cache miss, it queries PostgreSQL, retrieves the URL, populates Redis with a Time-To-Live (TTL), and then returns the URL. Before responding, the service publishes an asynchronous internal `UrlClickEvent` to log the telemetry data. Finally, it returns an HTTP `302 Found` response with a `Location` header pointing to the original URL.

### Phase 2: Core Spring Boot Architecture & Java Mechanics

**5. Explain how you structured the 3-tier architecture (Controller, Service, Repository) in Spring Boot.**
The architecture strictly follows the Separation of Concerns principle. 
- **Controllers (`@RestController`)** handle the web layer: parsing HTTP requests, triggering validation, and returning JSON responses with appropriate HTTP status codes.
- **Services (`@Service`)** encapsulate the business logic, transaction management (`@Transactional`), and caching rules. They act as the bridge between the web layer and the data layer.
- **Repositories (`JpaRepository`)** abstract the SQL data persistence, allowing us to interact with PostgreSQL using Java methods instead of raw SQL queries.

**6. How did you implement the Base62 encoding algorithm in Java, and why choose Base62 over hashing (MD5/SHA-256)?**
Base62 uses a 62-character alphabet (`[0-9, a-z, A-Z]`) which is entirely URL-safe, avoiding problematic padding characters like `+`, `/`, or `=` found in Base64. We convert the database's auto-incrementing Base-10 ID into a Base62 string using standard mathematical division and modulo operations. This guarantees zero collisions and deterministic, short lengths. Hashing algorithms like MD5 or UUID generate unnecessarily long strings and carry a mathematical (albeit small) risk of collisions, requiring extra database checks.

**7. How do Spring Data JPA and Hibernate map your Java entities to PostgreSQL tables?**
We use annotations like `@Entity` and `@Table` to mark a Java class as a database table representation. `@Id` and `@GeneratedValue(strategy = GenerationType.IDENTITY)` tell Hibernate that the primary key is auto-generated by PostgreSQL's `BIGSERIAL` sequence. When the application boots up, Hibernate reads these annotations and manages the persistence context, translating our Java object state changes into `INSERT`, `UPDATE`, and `SELECT` SQL statements.

**8. How do you validate incoming requests, and how does your global exception handler work?**
We use Jakarta Bean Validation annotations like `@NotBlank` and `@Pattern` (with a regex for URLs) directly on our Data Transfer Objects (DTOs). If a payload fails validation, Spring throws a `MethodArgumentNotValidException`. We intercept this, along with custom exceptions like `UrlNotFoundException`, using a `@RestControllerAdvice` class. This global handler formats the errors into standardized, clean JSON responses instead of exposing ugly Java stack traces to the client.

### Phase 3: Performance, Caching & Concurrency

**9. How exactly did you implement caching using Redis?**
We use the Cache-Aside pattern via Spring's `StringRedisTemplate`. When a request for a short code comes in, we explicitly query Redis first using `redisTemplate.opsForValue().get(key)`. If it's null (a miss), we query the database and then use `.set(key, value, TTL)` to cache the result for 24 hours. When a URL is deleted, we explicitly call `.delete(key)` to evict it from the cache, ensuring stale data is never served.

**10. How do you prevent a 'Cache Stampede' if a viral shortened link expires from Redis?**
Currently, the TTL provides basic expiration. To prevent a stampede (where thousands of concurrent requests hit the database simultaneously for a missing key), we would implement Mutex locking using Redis `SETNX`. The first thread to experience the cache miss acquires the lock, queries the database, and repopulates the cache, while other threads wait briefly and then retry the cache.

**11. Why should the analytics tracking be asynchronous, and how did you configure `@Async`?**
Synchronous database writes take time (e.g., 20–50ms). If we waited for the telemetry to save before redirecting the user, the application would feel sluggish. By using Spring's `@EnableAsync` and `@EventListener`, we decouple the processes. The redirect thread fires an event and immediately returns the 302 response to the user. A separate background thread, managed by a custom `ThreadPoolTaskExecutor` defined in our configuration, picks up the event and performs the database `INSERT`.

**12. What happens if the internal async task queue fills up when click traffic spikes?**
If the thread pool queue hits its maximum capacity, Spring respects the configured `RejectedExecutionHandler`. By default, this might throw an exception. A better policy is `CallerRunsPolicy`, which forces the thread that fired the event (the web thread) to execute the task, naturally throttling the system (Backpressure). At enterprise scale, we would replace in-memory Spring events with an external message broker like RabbitMQ or Kafka.

### Phase 4: Database Design, Transactions & Scalability

**13. What database indexes did you create in PostgreSQL, and why?**
We placed a unique constraint (which inherently creates a B-Tree index) on `urls.short_code` to ensure rapid $O(\log N)$ point lookups when redirecting users. In the future, a composite index on `url_analytics (url_id, click_time DESC)` would be added to power fast range scans for the telemetry dashboard, ensuring analytics queries don't require full table scans.

**14. Why did you use HTTP 302 Found instead of HTTP 301 Moved Permanently for redirection?**
An HTTP `301` instructs the browser to cache the redirect permanently. Subsequent clicks by the user bypass our server entirely, ruining our ability to track click analytics. An HTTP `302` (Temporary Redirect) forces the browser to hit our backend on every single click, ensuring our telemetry data remains 100% accurate.

**15. How do transactions work in your service? What does `@Transactional` actually do?**
When a method is annotated with `@Transactional`, Spring AOP (Aspect-Oriented Programming) creates a dynamic proxy around the service bean. When the method is called, the proxy intercepts it, opens a database connection, and disables auto-commit. If the method executes successfully, the proxy commits the transaction. If any `RuntimeException` is thrown, the proxy automatically rolls back the transaction, ensuring data integrity.

**16. How does your service capture user metadata without heavy third-party dependencies?**
We capture user metadata by parsing HTTP headers provided natively by the `HttpServletRequest` object. We extract the `User-Agent` header to identify the device and browser, and the `Referer` header to determine the traffic source. If deployed behind a Load Balancer, we would check the `X-Forwarded-For` header to resolve the true client IP address.

### Phase 5: Edge Cases, Security & Production Readiness

**17. How do you protect this service from malicious users?**
At the API level, we utilize regex validation to ensure only properly formatted HTTP/HTTPS links are processed. For production, we would implement IP-based rate limiting using a token bucket algorithm (e.g., via the Bucket4j library and Redis) to prevent spamming. We would also implement domain blacklisting to prevent the shortening of known phishing or malware sites.

**18. If this service had to scale to 100 Million URLs per month, what bottleneck would you hit, and how would you fix it?**
The first major bottleneck would be database contention on the auto-incrementing ID generation. Distributed systems struggle with single-point serial generation. To fix this, we would replace the PostgreSQL sequence with a distributed ID generator, such as Twitter Snowflake or pre-allocated ID ranges via ZooKeeper/Redis. This allows multiple application instances to generate unique IDs independently without database coordination.

**19. How did you containerize this application?**
The infrastructure (PostgreSQL and Redis) is containerized using `docker-compose.yml`, which networks the services together and injects necessary environment variables (like passwords and ports) automatically. This ensures the application runs identically on any developer's machine without manual database installation.

**20. What was a technical bug or hurdle you faced, and how did you fix it?**
One notable hurdle is the greedy matching of the `@GetMapping("/{shortCode}")` in the `RedirectController`. Initially, it was intercepting requests for static files like `index.html` and returning 404 JSON errors because it thought "index.html" was a short code. I fixed this by restricting the path variable with a regex: `@GetMapping("/{shortCode:[a-zA-Z0-9]+}")`, ensuring it only processes valid alphanumeric Base62 codes and allows static assets to load correctly.
